Case study

Testing AI agents for prompt injection

AgentShield is an open-source test harness I wrote. It checks whether an AI agent with tools (email, files, a database) can be tricked by text it reads, and which defenses stop that.

Why I built it

More products now give a language model access to tools. If the model reads a web page, an email or a document that contains hidden instructions, it may follow them. That can mean sending customer data to an outside address or reading files it should not touch.

I wanted a small, repeatable way to measure how often that happens and which defense prevents it, instead of relying on one-off demos.

How it works

  • 30 attack cases in 6 groups: direct injection, indirect injection, injection through retrieved documents (RAG), injection through tool output, multi-turn manipulation, and unauthorized tool use.
  • Each case has a policy the agent should follow, the attacker's text, the safe behaviour I expect, and rules that decide whether the attack worked.
  • The tools are fake. Messages go to an in-memory list, files and database tables are made up, and the secrets are marker strings. Nothing leaves the test.
  • Five defenses can be switched on in any combination: input sanitization, separating trusted and untrusted text, checking every tool call against the policy, asking the user before sensitive actions, and scanning output for secrets.
  • Outcomes are decided by fixed rules, not by another AI model. Every rate shows its count and a 95% Wilson interval.
  • It can also call any OpenAI-compatible API, so the same cases can run against a real model or a staging agent.

What I took from it

  • Checking tool calls against the policy did the most. Authorization alone took successful attacks from 9 to 1, because it blocks the call even after the model has been fooled.
  • Sanitization and separation each stopped about half. Attacks that don't match a known pattern still got through.
  • No single defense got to zero. All five together did, and no normal task broke.
  • 30 cases is a small sample. Even 0 of 30 has a 95% interval up to about 11%, so treat these as signals, not proof.

How the demo is built

  • The core engine uses only the Python standard library.
  • The demo is a FastAPI app. Requests are validated strictly (known defense names only, a fixed case-id format, a 4 KB size limit) and errors come back as JSON.
  • Responses carry security headers, including a Content-Security-Policy that blocks inline scripts and framing.
  • Attack text is always shown as plain text in the browser, so it can't run as code. A test checks this.
  • No API keys, no outside calls, nothing stored.

Limitations

  • The mock agent is a simulator. Real models fail in less predictable ways, which is why the harness also supports real endpoints.
  • With 30 cases, pattern-based defenses can look better than they would against a determined attacker.
  • Giving the mock agent extra tools made no difference here, because its behaviour depends on the attack text. A real model may behave differently.

Testing your agent

If you are building an agent that reads outside content and can take actions, I can run this kind of test on your staging setup:

  1. List the agent's tools and data, and what it must never do.
  2. Adapt the attack cases to your tools and add ones specific to your product.
