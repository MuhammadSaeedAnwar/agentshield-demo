Case study

Measuring prompt-injection risk in AI agents that can send email, read files and query databases

AgentShield is an open-source evaluation harness I built to answer one practical question: if untrusted text reaches an AI agent, does the agent misuse its tools, and which defenses actually stop it?

The problem

Teams are wiring language models to real tools: email, file storage, CRMs and internal databases. The risk is not a rude chatbot reply. It is an agent that reads a web page, a support ticket or a retrieved document containing hidden instructions, and then quietly sends customer data to an outside address or calls a tool it was never meant to use.

Most evidence on this is either a one-off exploit demo or a vendor claim that a guardrail "works". Neither tells a team how often their setup fails, or which control to fix first.

What I built

  • 30 attack cases in 6 categories: direct prompt injection, indirect injection, RAG (retrieved document) injection, tool-output injection, multi-turn manipulation and unauthorized tool use. Each case has a deployer policy, an attacker payload, an expected safe behaviour and machine-checkable success criteria.
  • A simulated tool environment with messaging, file, database, document-search, calculator and weather tools. Nothing leaves the sandbox: "sent" messages go to an in-memory outbox, files and tables are fake, secrets are canary strings.
  • Five composable defenses: input sanitization, trust-boundary separation, tool authorization against a policy, user confirmation for sensitive actions, and output validation (an egress filter for secrets).
  • Rule-based scoring, not an LLM judge. Every episode is classified from what the agent actually did, and every rate is reported with its numerator, denominator and a 95% Wilson interval.
  • An adapter for any OpenAI-compatible endpoint, so the same cases can be run against a real model or a client's staging agent.

What this shows

  • Enforcing policy at the tool layer did the most work. Authorization alone cut successful attacks from 9 to 1 because it blocks the dangerous call even when the model has been fooled.
  • Prompt-level defenses help but leak. Sanitization and separation each stopped about half of the successful attacks. Attacks that do not match a known pattern still get through.
  • Layering matters. No single defense reached zero; all five together did, without breaking any benign task.
  • Small sample, wide intervals. With 30 cases, 0/30 still has a 95% interval up to about 11%. These are indicative results, not proof of safety.

Engineering

  • Core engine uses only the Python standard library, so a reproduction run cannot break on a dependency update.
  • This demo is a FastAPI service with request validation (strict schemas, allowlisted defense names, case-id pattern, 4 KB body limit), JSON error responses, and security headers (CSP, no framing, no sniffing).
  • The frontend renders attack payloads as plain text only, so payloads in the dataset can never run in the browser.
  • No API keys, no outbound calls, no user data stored.

Limitations

  • The mock agent is a simulator. Real models fail in less predictable ways, which is why the harness also supports real endpoints.
  • 30 cases is a small dataset. Pattern-based defenses can look better here than against a determined attacker.
  • Giving the mock agent every tool (over-provisioning) made no difference in these runs, because its behaviour is driven by the payload. A real model may behave differently.

Testing your agent

If you are building an AI agent that can read untrusted content and take actions, I can run this kind of assessment against your staging setup:

  1. Map the agent's tools, data sources and what it must never do.
  2. Adapt the attack cases to your tools and policies, and add cases specific to your product.
